# test-case-to-script: pseudocode -> executable pytest+Appium code

Land pseudocode into runnable iOS automation scripts. **Key constraint: after generating, the user must debug; only save the case after debugging passes.**

## Trigger entries

Two ways to enter this Skill:

1. **Give pseudocode directly**: the user has pasted/written the pseudocode; land it directly.
2. **"Implement a feature" command**: the user says "implement `CNAPP-611` feature / land `<JIRA_KEY>` into code". In this case, **first find the corresponding pseudocode in `tests/mobile/ios/pre_code/<JIRA_KEY>.md`** (same-name match, e.g. "implement CNAPP-611" -> `tests/mobile/ios/pre_code/CNAPP-611.md`), read the scenario header, numbered step details, and inline locator snippets, and generate code only after **obtaining enough information**; when element details are insufficient, go back to `tests/mobile/ios/pages/`. **If the corresponding pseudocode is not found in `pre_code/`, do not fabricate it** - prompt the user to first go through `test-case-authoring` (pull the case from the Jira MCP to generate pseudocode).

> **Search order when checking the page element knowledge base (always "navigation page first -> specific page second")**: when the element info in the pseudocode/Page Object is insufficient and you need to verify a page's control facts against the Confluence page element knowledge base, **you must first use `Atlassian-MCP-Server`'s `getConfluencePage` to read the [iOS Page Map & Inventory navigation doc](https://marriottcloud.atlassian.net/wiki/spaces/~712020dbd6441f05734e4da1386119f88cfbe0/pages/4280157316) (pageId `4280157316`)** - it is the knowledge base entry: Section 2 page relationship map + Section 3 page inventory (slug / page name / login state / element count / doc link). First locate the needed page and its doc link in the navigation page, **then click into the corresponding `iOS Page Elements - <Page Name> (<slug>)` doc under the [page_doc folder](https://marriottcloud.atlassian.net/wiki/spaces/~712020dbd6441f05734e4da1386119f88cfbe0/folder/4280157634/page_doc) to view the specific element table**. ⛔ Element locator landing still follows the Page Objects under `tests/mobile/ios/pages/` as the single source of truth; the knowledge-base docs are only for fact verification / gap-filling reference; if the navigation doc lacks that page, point back to `test-case-authoring`'s missing-element collection gate.

## Handoff contract with `test-case-authoring` (the most important related logic, must follow)

This Skill's input is `test-case-authoring`'s **two artifacts**: `pre_code/<JIRA_KEY>.md` (with the scenario header, numbered step details, inline locators, and a trailing **"page & element locator gap list"**) and `features/<JIRA_KEY>.feature`. **When landing steps, use the gap-list tier as the execution contract**, deciding step by step whether to "really implement" or "placeholder":

- **ready (the list names a reusable Page Object + usable elements/methods)**: **must truly connect to the Page Object and implement** - call the existing method/locator named in the list (e.g. `view_rooms()`, `fill_guest_info()`, `GUEST_INFO_TITLE`, optional fields `CITY_INPUT`/`STREET_ADDRESS1_INPUT`), turning this feature step into a runnable real call chain. **It is strictly forbidden to still write a `NotImplementedError` placeholder for a "ready" step** (that would discard the results authoring prepared and make static collection "look passing" while nothing is actually implemented).
- **partially missing / pending real-device re-check (page built, a few display/stable-flag locators used for dynamic assertions pending check)**: **connect to the existing locators for real calls**, but for the "pending check" locators use **gentle degradation** - run with the existing locator first, assert using normalized "mutual containment" rather than strict equality (RULE_008), and clearly annotate in the step docstring with `⚠️ ... pending real-device re-check` pointing to `test-page-elements`; **do not `NotImplementedError` the whole thing**.
- **fully missing (a whole page with no matching existing page / key interaction locators entirely absent)**: normally this gap should already have been collected and filled by `test-page-elements` in `test-case-authoring`'s "⛔ Missing-element collection gate"; **if fully missing is still found at this stage (meaning the user chose "skip placeholder" or missed collecting in authoring), first prompt the user "these steps still lack elements; I suggest going back to `test-case-authoring`'s missing-element collection gate to connect a real device and fill"**, and only write `NotImplementedError` (or a minimal placeholder) if the user insists on continuing, clearly telling the user "which step lacks what and must be filled via `test-page-elements` first"; **do not fabricate locators out of thin air**.

> In one sentence: **"ready" must be really implemented, "partially missing" is really implemented + gently degraded + annotated, and only "fully missing" is placeholdered.** Before landing, read the whole gap list in `pre_code/<JIRA_KEY>.md`, align each step with the list before acting; if during implementation you find a "ready"-marked method/locator does not actually exist, go back and verify against the Page Object, do not degrade straight to a placeholder.

## Output landing conventions (must follow)

- **Step definitions are split by "page" (core convention, must follow)**: **do not create one `<jira_key>_steps.py` per Jira Key**; instead, **one-to-one with Page Objects, by page**, land into `tests/mobile/ios/steps/<page>_steps.py` (e.g. hotel detail page -> `property_detail_steps.py`, room rate list page -> `room_list_steps.py`, review booking page -> `review_booking_steps.py`, guest info page -> `guest_info_steps.py`; home -> `home_steps.py`, hotel list -> `property_list_steps.py`, fully consistent with the existing `home_steps.py`/`property_list_steps.py`/`landing_steps.py` style). **Each step belongs to the page where it actually operates/asserts**, and that file only `import`s that page's Page Object. **The feature combines the generic steps scattered across page files across pages via BDD** - the same page step can be reused by multiple features and is not bound to any single Jira Key. **Keep an `XxxSteps` class extending `BaseSteps` at the end of each `<page>_steps.py`** (consistent with existing files).
- **Jira traceability**: keep the `# jira: <JIRA_KEY> | <url>` comment in the feature file header as that case's traceability; **step files no longer write a `# jira:` header, nor `scenarios(...)`** - steps are generic assets reused by page, and features are registered one by one via `plan/debug.py`.
- **Export**: after creating any `<page>_steps.py`, append `from .<page>_steps import *` to `steps/__init__.py` (no need to re-append when reusing an existing page file).
- Page Object / page elements: put them under `tests/mobile/ios/pages/`, like other pages, as **class-attribute tuple locators of the corresponding script Class, at the top of that Class** (consistent with the existing style of `login_page.py`/`account_page.py`). **Prefer reusing a semantically matching Class in an existing page (login_page/home_page/account_page/landing_page, etc.)**; only when there truly is no matching existing page, **you may create a new page file** to hold that page's elements (do not create one file per page per Jira Key). **`<page>_steps.py` and `<page>.py` (Page Object) should keep a one-to-one page-semantic correspondence.** The class extends `base_pages.BasePages`, reusing `self.click/input_text/wait_until_*/is_element_displayed/switch_to_tab`.
- If the feature does not exist yet or needs updating, write/update it to `tests/mobile/ios/features/<JIRA_KEY>.feature` (flat by default; `features/<domain>/<JIRA_KEY>.feature` as cases grow).
- **feature registration**: append a line `scenarios(feature_dir.joinpath("<JIRA_KEY>.feature").as_posix())` in `tests/mobile/ios/plan/debug.py` (aligned with Android `plan/debug.py`).

> **This Skill is the sole production entry for these steps/Page Objects/features (hard constraint)**: `tests/mobile/ios/steps/<page>_steps.py`, the corresponding Page Objects, and `<JIRA_KEY>.feature` **can only be produced/updated by this `test-case-to-script` flow**, and **you must have the corresponding pseudocode (`pre_code/<JIRA_KEY>.md`) before acting** - do not hand-write or fabricate these files in advance without going through this flow or without pseudocode. If there is no pseudocode yet, go through `test-case-authoring` first and come back.

> **Only protect the "project's existing legacy files" (hard constraint)**: do not modify **legacy files already present in the current project** - do not touch `tests/mobile/ios/features/debug.py`, `tests/pytest.ini`, any file on the Android side, and the existing iOS `conftest.py`/`pages`/`steps`, etc. **Files newly created by this flow, and files added later, may be freely modified/appended** (e.g. append `scenarios(...)` to the newly added `tests/mobile/ios/plan/debug.py`, update the feature/steps/Page Object newly written this time). The run entry is unified via the **newly added** `tests/mobile/ios/plan/debug.py`; new files prefer to fit the existing iOS parent sample (reference the Android framework).

## Pipeline position

Last segment of the main line: Jira case -> pseudocode (`test-case-authoring`) -> **pseudocode -> pytest+appium code** -> debugging (`test-debug-script`).

## Project structure conventions (current framework ground truth)

- `tests/mobile/ios/features/*.feature`: Gherkin scenarios (English keywords + Chinese steps); **registered via the newly added `tests/mobile/ios/plan/debug.py`** (one by one `scenarios(...)`, aligned with Android `plan/debug.py`), **does not modify** the existing `features/debug.py`
- `tests/mobile/ios/steps/<page>_steps.py`: `@given/@when/@then` bindings **split by page** (one-to-one with Page Objects, e.g. `property_detail_steps.py`/`room_list_steps.py`/`review_booking_steps.py`/`guest_info_steps.py`, aligned with the existing `home_steps.py`/`property_list_steps.py`/`landing_steps.py`); **not one file per Jira Key**; features combine these generic steps across pages via BDD. `(driver, ...)` takes conftest's `driver` fixture directly and calls that page's Page Object; export via `from .<page>_steps import *` in `steps/__init__.py`. Keep an `XxxSteps` class extending this directory's `base_steps.BaseSteps` at the end of each file (note: iOS `conftest.py` uses `tests.mobile.android.steps.base_steps.BaseSteps` for screenshots, which is existing style - do not change)
- `tests/mobile/ios/pages/`: Page Objects extend `base_pages.BasePages`, with page elements as **class-attribute tuple locators at the top of the corresponding Class** (consistent with existing pages); prefer merging into an existing/semantically matching Class, and only when there truly is no match create a new page file
- Connection/account: `config/env/.env.ios.lle` + `tests/mobile/ios/conftest.py` (provides the `driver` fixture, auto screenshot on failure, login per marker); **do not use `config.py`, do not build capabilities/sessions yourself**
- marker: **only use those registered in `tests/pytest.ini`** (`@GuestUser`/`@MemberUser`/`@PlatinumUser`/`@resetAPP`/`@mockAPI`, etc.), **do not write `@ios`** (unregistered will warn)

## Generation conventions

- Prefer `AppiumBy.ACCESSIBILITY_ID`, then `IOS_PREDICATE` / `IOS_CLASS_CHAIN`, with `XPATH` as fallback; for anything uncertain, use a placeholder and **clearly tell the user it needs replacing**.
- Page Objects extend `BasePages`, locators are class-attribute tuples, reuse `self.click/input_text/wait_until_clickable/wait_until_displayed/is_element_displayed/switch_to_tab`, do not reinvent wait/click wheels.
- Steps use `parsers.parse('... "{var}" ...')` to pass params; assertions are semantically clear with Chinese error messages.
- Reuse the existing conftest's `driver` fixture and the style of `tests/mobile/ios/pages/login_page.py`, do not reinvent wheels; tags only use markers registered in `tests/pytest.ini`.
- **Division of the two memories (keep clear)**: `test_case_memory.yaml` = **understanding layer / step breakdown** - when the user-written scenario steps are underspecified (high-level/vague/omitting intermediate ops), **precisely break down the implementation logic per the user's habits** (what UI sub-operations a high-level step expands into, in what order); `test_script_memory.yaml` = **implementation layer / code running** - general technical rules that keep the generated script's code logic stably running (wait/locate/assert/stability). In one sentence: the former governs "whether the breakdown is right (understanding the user)", the latter governs "whether the code runs". Before landing a step, check `test_case_memory.yaml` first; if its `step_pattern` hits the current (vague) step, generate sub-operations **in the recorded `breakdown` order** (specific locators still follow the Page Object / real device); if the user expresses a new "this is how I'd actually break down this kind of underspecified step" in this implementation, abstract it into a `CASE_xxx` and append to `test_case_memory.yaml`.
- **When selecting a list object whose identity is irrelevant, uniformly "take the first card + reuse dynamically" (`CASE_002`)**: whenever selecting/operating an object on **any level of list/selection page** where the object's specific identity is irrelevant to the case's real goal (just getting the flow through / verifying some field text) - **property, room (e.g. "Room, 1 extra-large bed"), rate (e.g. "flexible-change rate") treated equally**: remove the hard-coded object name/spec column from Examples, and instead "after the list page of that level is shown, capture the first card's info (index=0) -> tap the first card (not relying on name/spec) -> compare dynamically against the runtime-captured value downstream". Keep the hard-coded value only when the assertion **strongly depends** on a specific object's identity.

> Please check/modify as needed, then run on a real device to verify:
> `.venv/bin/python -m pytest tests/mobile/ios/plan/debug.py -v --app-platform ios`
> Reply "debugging passed" after it verifies and I'll formally save this case; if it fails or needs adjusting, paste the error/notes and I'll fix the locators or logic accordingly.

**Before the user explicitly replies "debugging passed", do not claim the case is done, and do not move to the next case.** If the user reports failure or asks for changes, fix per the feedback, re-run the static self-check, and ask to verify again; only append one general rule to `.cursor/profiles/test_script_memory.yaml` if cross-case general experience is distilled from it.

**Handoff to `test-debug-script`**: once the user starts real-device debugging (or reports an error/stuck), **enter `test-debug-script`** - systematically locate the failure -> make a minimal fix -> ask the user to rerun; after debugging passes, `test-debug-script` completes the "record user feedback -> abstract -> user confirms -> write back to `.cursor/profiles/test_script_memory.yaml`" distillation loop, no need for the user to name it again. **When `ai-test-agent` is orchestrating the main line**, still obey that Agent's per-step `AskQuestion` gates: after this Skill delivers executable code, stop for user confirmation before entering `test-debug-script` (do not chain Skills in one turn without an explicit user choice).
