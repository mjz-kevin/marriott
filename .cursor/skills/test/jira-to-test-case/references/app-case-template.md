# iOS Test Case Specification (4 Test-Point Types / Fields / Steps)

This page is the **specification for the body of an iOS functional test case**: it defines how every single case should be written (test-point classification + field columns + step-writing rules). **All iOS test-case pages (published into the `{epic}-TestCase` folder beside the Tech Solution) are auto-generated by the `jira-to-test-case` skill (app target) according to this specification** — before generating, the AI reads this spec and produces cases following the three test-point types, field columns and step requirements here; **no manual copying required**.

**Language (hard):** all case content the skill authors itself is written in **English** (titles, section headings, test title / preconditions / test steps / expected result / notes). The only exception is **on-screen app control text quoted verbatim** (button / tab / field labels captured in the `page_doc` element docs, e.g. "目的地", "查找酒店", "继续") — these stay in Chinese and are quoted, because the tester must see the exact on-screen copy. Do not author a whole page in Chinese.

This page only governs "what a single case looks like". Everything else — **page naming, the whole-page section structure, page-fact retrieval, the generate-and-publish flow, the confirmation gate, and handoff to implementation — is maintained in the `jira-to-test-case` skill, not here.**

The whole case page is now a **slim structure: a traceability header + 5 sections** (Requirement Overview / Change Points & Scope Analysis / Dependencies & Assumptions / Historical Defects & Regression / Functional Test Case List). **One requirement = one Confluence page** — no parent-framework + child-case split, and **no separate coverage-matrix / coverage-self-check / page-fact-gap sections**; traceability and page-fact gaps are merged into Dependencies & Assumptions and the case Notes column. That whole-page structure is defined in the skill, not here.

> ⛔ **AI-assistance declaration (first line of the published body — hard):** the AI-generated local Markdown body's **very first line** must be the verbatim quote block `> This document was created with AI assistance.`, placed at the absolute top — **above** the traceability header and all 5 sections. Use exactly that English text (no translation, no rewording, no emoji). Keep it as the first line (and keep exactly one copy) on every re-publish / in-place update — never drop or duplicate it. ⚠️ This belongs at the **top of the page body only** — do **not** put it inside the case-list table or any field cell. (The whole-page layout and this declaration's placement are owned by the skill; this note only mirrors it for context.)

To change the test-point / field / step rules for a case, **edit only this file**; it takes effect automatically on the next generation.

## 1. The three test-point types (every case page must cover)

Every case page **must cover all three types below**; if any is missing, state the reason explicitly in the case **Notes column** or in a line at the end of the **Functional Test Case List** (there is no longer a separate coverage self-check section):

| Test-point type | Meaning | Typical focus |
| --- | --- | --- |
| Data | Data input / validation / storage / redisplay / boundaries and exceptions | Required/optional, format validation, max length, special characters, empty values, persistence and redisplay on re-entry, rendering of API-returned data |
| Function | Whether the core business flow and logic are correct | Happy-path main flow, negative/exception flow, business rules, permission/user-type differences, state transitions |
| UI | Interface presentation and interaction | Layout/copy/icons, control states (default/disabled/selected/loading/empty/error), cross-platform consistency, tap feedback |

## 3. Step-writing requirements (important)

The quality of a case lives in the **Test steps** and **Expected result** columns. **Steps that are too terse are the single most common defect** (e.g. "1. type 30 chars; 2. tap save"). Follow these rules strictly — a tester must be able to execute the case on the real device without guessing anything.

**Minimum detail bar (hard — every step must satisfy all of these):**

- **Start from a navigation entry point.** The first step(s) must state **where in the app the tester is / how they got to the screen under test** — the tab, page, or navigation path they open (e.g. "In the bottom nav tap "账户" to enter the account page", then "Tap "个人资料" to enter user_profile_page"). Never start mid-screen assuming the reader already knows where they are. Align the entry to a `page_doc` slug where possible.
- **One concrete user action per step**, numbered one by one, in the real order a tester taps. Each step must name the **action + the exact on-screen control (verbatim label text, quoted)** — e.g. "In the home "目的地" input, enter a destination city", "Tap the first matching city in the suggestion list", "Tap the "查找酒店" button". Not a vague "operate the page" / "search a destination".
- ⛔ **Do not provide specific input data in the steps.** AI-made sample values (literal strings, city names, numbers) add no value — the tester picks the actual data at execution time. Describe the input only by its **kind / constraint that the case verifies** (e.g. "enter a valid destination", "enter a keyword with no results", "enter a name at the maximum length allowed by the requirement"), never a literal value like "上海". A limit / threshold from the requirement may be named as the rule under test; the literal test string may not. Still state the **action that triggers validation** (clear the field + tap "继续" / tap "保存").
- **Use the exact on-screen control text, kept verbatim and quoted** (Chinese app copy stays Chinese) — button / tab / field label / cell title / toggle. Prefer a concrete control aligned to the `page_doc` element facts; where a doc fact is missing, use a semantic description (e.g. "Tap the "查找酒店" button") and note "element to be captured on device" in the **Notes** column — do not invent a locator.
- **A functional/flow case needs ≥ 3 steps** covering entry → operation → the action that commits/verifies (enter the page → perform the operation → submit / confirm / observe). A pure single-field data/boundary case may be shorter but must still include the entry step + the trigger action. If you find yourself writing only 1–2 ultra-short steps, you are under-specifying — expand them.
- **Expected result is observable and maps to the steps** — number it per point for multi-step cases; each line is something the tester can see (navigates to X page / the title shows the selected city / a required-field error appears under "名字" / the button is disabled / empty-state copy "未找到酒店" shows). Avoid a bare "normal/success" with no observable detail.
- Do **not** invent elements/rules you are unsure of; note the reason in the "Notes" column.

**Bad vs. good (same required-field check):**

| ❌ Too terse (reject) | ✅ Detailed enough (required) |
| --- | --- |
| **Test steps:** 1. clear name; 2. tap continue **Expected:** error | **Test steps:** 1. In the bottom nav tap "预订" to enter the Guest Info page (guest_info_page); 2. Tap the "名字" input and clear its existing content; 3. Tap the "继续" button at the bottom of the page **Expected:** 1. The Guest Info page opens, showing the "名字/姓氏" inputs; 2. The "名字" input is cleared; 3. A required-field hint (e.g. "请输入名字") appears under the "名字" input, the page stays on Guest Info and no navigation occurs |

Step-style example (user-action style, control text kept verbatim in Chinese):

- `1. In the bottom nav tap "账户" to enter the account page (account_page)`
- `2. Tap the home "目的地" input`
- `3. Enter a destination city`
- `4. In the suggestion list tap the first matching city`
- `5. Tap the "查找酒店" button`

## 4. `Regression` and `Automation` judgement rules (AI marks true / false per case)

Two of the case columns are **AI-made boolean judgements** — the AI must set each to `true` or `false` for every case, and record the reasoning in **Notes** whenever the call is not obvious.

### 4.1 `Regression` (is this a regression case?)

- **Definition**: a regression case is one that **should be re-run whenever other, later feature changes land** — a stable, long-lived check of a **core / shared / cross-feature flow** whose breakage would be a serious, recurring risk. It is *not* a one-off verification of the brand-new behaviour this requirement introduces.
- **Mark `true`** when the case exercises: a core business main flow (search → list → detail → booking, login, payment entry, etc.); a shared component / widely-reused page; a known historical high-risk point; a navigation path many features depend on.
- **Mark `false`** when the case only verifies **this change's own new/edited behaviour** (new field, new copy, this-change empty state), a low-value cosmetic UI point, or a narrow one-off boundary that no later change would plausibly affect.
- When uncertain, lean on: "if an unrelated feature changes next sprint, would we still want to run this?" — yes ⇒ `true`.

### 4.2 `Automation` (should this case be automated?)

`Automation` is a **narrower** flag gated by `Regression`. Mark `true` **only if ALL** of the following hold; otherwise `false`:

1. **`Regression` is `true`** — a case that is not a regression case is **never** `Automation = true` (there is no point automating a one-off check). If `Regression = false`, `Automation` is `false` automatically.
2. **No third-party-software step** — the case can be executed end-to-end **inside the app under test alone**, without driving or depending on any external app / system. Disqualifying examples: entering an SMS / email verification code, a third-party payment or bank app, a third-party login (WeChat / Apple / Google), jumping to the system Settings / camera / photo library, a push coming from another app.
3. **No asynchronous step** — the case has **no step that waits on a non-deterministic async outcome** that cannot be reliably awaited in-app: a backend job / delayed callback, a message / push arrival, an email delivery, an "eventually consistent" state change, or any "wait N minutes then check" step.

- If `Regression = true` but the case hits any third-party-software step or any asynchronous step, mark `Automation = false` and name the disqualifying step in **Notes** (e.g. "needs SMS code — third-party step", "waits on async booking-confirmation push").
- A clean, deterministic, in-app regression flow (pure navigation / input / on-screen assertion) is the ideal `Automation = true` candidate.

> **Consistency rule (hard)**: `Automation = true` ⇒ `Regression = true`. The AI must never emit a case with `Automation = true` and `Regression = false`.

## 5. `Domain` judgement rule (AI fills by default)

The `Domain` column is an **AI-made single-choice judgement** — set it for **every** case to exactly one **leaf value** from the detailed enum below. The enum mirrors the **CN Bonvoy App Test Case Repository** folder tree (two-level in Confluence, flattened to a single-level leaf list here), so each case traces to the concrete business module it exercises.

- **Values (fixed enum — do not invent others; this list is the full set, taken verbatim from the repository folder tree)**:

  | Leaf value | Owning top-level group | Note |
  | --- | --- | --- |
  | `Commerce` | Commerce | the group itself, use when a Commerce case does not fit a specific sub-module below |
  | `Shop` | Commerce | search / hotel list / room / rate browsing |
  | `Book` | Commerce | booking flow (guest info / review / confirm) |
  | `iOS-Local Payment` | Commerce | iOS local payment |
  | `Android-Local Payment` | Commerce | Android local payment |
  | `Payment Console` | Payment Console | the group itself |
  | `PMS-MARSHA` | Payment Console | PMS / MARSHA |
  | `Content` | Content | the group itself |
  | `LaunchAds` | Content | launch / splash ads |
  | `Homepage` | Content | home page content |
  | `Discover` | Content | Discover tab content |
  | `NCP` | Content | NCP |
  | `Loyalty` | Loyalty | the group itself (membership tier / points / benefits) |
  | `Compliance` | Loyalty | compliance |
  | `Trips` | Trips | the group itself (trips / reservations management) |
  | `Platform` | Platform | the group itself (account / login / settings / app shell / cross-cutting) |
  | `Umeng` | Platform | Umeng SDK / tracking |
  | `MK` | MK | the group itself |
  | `Android-Saflok` | MK | Android Saflok |

- **Judge by the feature nature, not the title's literal words.** Pick the single **leaf** closest to the case's **core value** / the page & flow it exercises — e.g. search → list → detail → rate browsing ⇒ `Shop`; guest info / review / confirm a booking ⇒ `Book`; iOS payment screen ⇒ `iOS-Local Payment`; launch/splash ad ⇒ `LaunchAds`; home content ⇒ `Homepage`; account / login / settings / app shell ⇒ `Platform`; tracking/analytics via Umeng ⇒ `Umeng`.
- **Fall back to the top-level group value when the leaf is unclear.** If the case clearly belongs to a group (e.g. Commerce) but cannot be pinned to a specific sub-module (Shop vs Book), use the **group value itself** (`Commerce`) and state the reason in **Notes**. Never leave it blank and never use a value outside this enum.
- **Prefer the requirement's own domain signal when present**: if the source Jira Epic / Story already carries a `business_domain` label (one of the 4 top-level groups `Commerce / Loyalty / Trips / Platform`), use it to pick the **owning group**, then refine to the specific leaf by the case's feature nature; deviate only when a single case clearly belongs elsewhere, and note the reason in **Notes**.
- **Cross-module cases**: when a case spans more than one leaf, choose the one matching its **core value** (not the incidental steps), and note the cross-module nature in **Notes**.

> **Relationship with the Jira `business_domain` label and the bug `Domain` field (do not conflate — this case-table `Domain` is independent)**: this case-table `Domain` column uses the **detailed leaf enum above** and is **this (test-case) line's own field** — it is just Confluence table text, not bound by, and not the same source as, either Jira enum below:
> - The PO-side Jira **`business_domain` label** (profile `mcp.jira.labels.business_domain.values`) is a filter hard-gate on CNAPP that only accepts the **4 top-level groups** `Commerce / Loyalty / Trips / Platform`.
> - The Jira **bug `Domain` custom field** (profile `mcp.jira.bug.domain_values`) also uses the **4 top-level groups** `Commerce / Loyalty / Trips / Platform`.
>
> So the detailed leaf enum here is **test-case-only**; it is deliberately **not** propagated into the Jira label gate or the bug `Domain` field (those stay at the 4 groups). When a reader needs to relate a case's leaf to a bug/label, use the **owning top-level group** shown in the enum table (e.g. a `Shop` / `Book` case rolls up to `Commerce`).
