# jira-to-test-case: requirement -> requirement outline + functional test cases

This skill is a **standalone "test case design" main line**.
It reads a new requirement from a requirement source (**Jira MCP** `Atlassian-MCP-Server`, or a **requirement link** provided by the user),
**when checking the page element knowledge base, first reads the [Page Map & Inventory navigation page](https://marriottcloud.atlassian.net/wiki/spaces/DBU4/pages/4280157316) to locate the needed page, then enters the corresponding page under the [page_doc folder](https://marriottcloud.atlassian.net/wiki/spaces/DBU4/folder/4280157634/page_doc) for specific elements** (prefer the link when the user gives a page link directly);
**if not found in the knowledge base**, uses **Confluence MCP global search** for relevant pages and feature content;
then combines **existing cases** (Android / iOS `features/`), synthesizes the **frontend / backend scope** and **historical defect risk** this change involves,
and produces a reviewable **"requirement outline + functional test cases"** document, **published as a Confluence page into the `{epic}-TestCase` folder beside the Tech Solution** (folder mode `--root/--epic/--kind test_case`, sibling to `{epic}-Tech Solution`; see "Naming and publishing conventions"), as input for subsequent automation landing.

> **This skill's boundary (important)**: it only does **test case design** - requirement summary, scope analysis, risk/regression identification, test-point breakdown, case list.
> It **does not generate** `feature` / pseudocode / pytest scripts. Landing into executable scripts is taken by `test-agent`'s main line
> (`test-case-authoring` -> `test-case-to-script` -> `test-debug-script`).
> This skill is the **"case design" stage upstream** of that main line.

> **Confluence IDs come from the current profile (not hard-coded here)**: every Confluence destination/space/id this skill publishes to or reads from below — for both the app and cms targets — is resolved from the current team profile (resolve its path via `profile-select`'s `profile.py resolve`). The literal ids shown in links/commands/callouts below are only the current reference values. **Both targets now use the same landing mode — folder mode** on the team's shared requirement/solution tree (same `--root`/`--epic` as PRD/tech-solution, `--kind test_case`), differing only in each team profile's `root`/`space` value. ## Naming and publishing conventions (official artifact on Confluence; draft under `.ai-sdlc/jira-to-test-case/`)

> ⛔ **Publishing-implementation constraint (hard - applies to both app and cms - cannot be skipped)**: generating/publishing a case doc **must go through the shared Confluence publishing capability's upload script** (`~/.cursor/skills/common/confluence-publish/scripts/upload_confluence_v2.py`) in **folder mode** for both targets (`--root` = `mcp.confluence.parent_pages.root`; `--epic` = the Jira Epic key; `--kind test_case`; `--space` = `mcp.confluence.space`), which lands the case page inside the auto-ensured `{epic}-TestCase` folder, **sibling to `{epic}-Tech Solution`** on the team's shared requirement/solution tree. Current reference values: **app** root `4205314140`/space `DBU4` (app-test) or `4191912061`/`CMI` (app-prod); **cms** root `4205314140`/space `DBU4` (cms-test, shared with app-test) or `4175954245`/`CMI` (cms-prod).
> - **Why the script rather than a direct MCP page write**: a case page's body is large (10-column UAT tables, panel macros, dozens of rows) and regularly exceeds the MCP single-write limit; the script submits the complete body in one shot over REST, keeps per-column pixel widths so wide case tables stay readable, and is unaffected by whether the Confluence page-write tools are enabled. Credentials come from `mcp.json`'s `confluenceRest` - **never** passed on the command line.
> - **Forbidden** to write your own publishing script (e.g. `publish_*.py`, `*_update_*.py`), to build any bespoke "write an HTML body file, then POST/PUT it via curl/requests" relay, or to hard-code an Atlassian email / API token in any script or file. **Also forbidden: writing the page through any Atlassian MCP page-write tool** (`createConfluencePage` / `updateConfluencePage` / `createConfluenceContent` / `updateConfluenceContent`, including the versions exposed by the Cursor Atlassian plugin) — create *and* update both go through the script. The shared script is the single implementation - **do not copy it into this skill either**.
> - **Body format**: author the case body as a local **Markdown** file (the script converts it to Confluence storage HTML: tables with adaptive pixel column widths, lists, panels). Inside a case table cell, use a literal `<br/>` to separate the numbered steps, and `\|` for a literal pipe. A one-shot complete draft - do not append in many small steps.
> - **The local `.md` is the reviewable draft and publish input**: write it under **`.ai-sdlc/jira-to-test-case/{case_id}/docs/`** (git-ignored), show the path to the user at the pre-publish gate, then pass that file to the upload script after confirmation. The **official** artifact is the Confluence page; keep draft versions in `docs/` for audit and rework.
> - If the script reports an error (permission / parent missing / oversized), **stop and explain**, fix the cause or confirm a streamlining strategy with the user, then rerun the script; **do not** fall back to a hand-rolled REST call.
> - ⛔ **Dedupe to prevent duplicates (hard)**: the script **dedupes automatically** - pass the stable title prefix (`<prefix> - <JIRA_KEY>`, or the short requirement name when there is no Key) as `--title`, and the readable tail as `--title-tail`. The script matches an existing page inside the target folder **by the `--title` prefix only**, so a reworded tail updates that same page (and renames it) instead of creating a near-duplicate; `action` in the returned JSON tells you whether it was `create` or `update`. **Never** hand-build a second page for the same Key, and never produce `(2)`/`(copy)` suffixed pages. Because the prefix is the unique key, **keep the date/version out of it**.
>   - ⛔ **Merged multi-requirement page dedupe (when several requirements were merged into one page)**: the script's prefix dedupe only covers a single stable prefix, so for a merged page **first check by hand** whether the folder already holds a page carrying this Key combination - use `searchConfluenceUsingCql` (`title ~ "CNAPP-383" AND title ~ "CNAPP-5664"`) or `getConfluencePageDescendants`. If a page already carries exactly this combination -> publish with the **same `--title` prefix** so the script updates it; if only a **subset** exists (a prior single-requirement page, or an older merge with fewer Keys), **ask the user** whether to (a) extend that page into the new combined page (reuse its prefix), or (b) create the new combined page and leave the old one - do not blindly create a near-duplicate.
> - Confirm with the page link before and after publishing/updating that it lands on the **single** official page.
> - ⛔ **Read-back verification immediately after publishing (hard - skips blind waiting)**: the script returns `page_id` / `version` / `url` / `action` on success. **Immediately** `getConfluencePage` with that `page_id` to confirm `status=current` and `parentId` equals the target folder - **judge "whether publishing succeeded" by the fact in Confluence as the data source, not merely by whether the command exited 0**. Only after verification is publishing complete; then return the link to the user.
> - ⛔ **After an interruption/exception, check the data source first, then decide whether to retry (hard - avoid wasted waiting)**: if the publishing flow is interrupted (timeout, black-box sub-agent with no return, an error leaving it unclear whether the write landed), **the first reaction is not to blindly rerun**, but to **first use `searchConfluenceUsingCql` (`title ~ "<JIRA_KEY>"`) or `getConfluencePageDescendants` to list the target folder and directly check whether the page already exists** (a query takes a few hundred ms).
>   - Exists with complete content (`status=current`, has the case list) -> **judge it done directly**, return the link to the user, **do not rerun**.
>   - Exists but incomplete / an empty draft -> rerun the script with the **same `--title` prefix**; it will update that page in place (never creating a second one).
>   - Confirmed not to exist -> only then rerun the script to create it.
>   - ⚠️ Especially when this skill is **executed black-box by a sub-agent (e.g. `test-agent`)**: an interrupted sub-agent only returns "task interrupted" **without the intermediate output**, while the page may already be written - **the upstream main agent must first check the Confluence data source to confirm, not conclude failure and resume the task just because "the sub-agent did not return success", causing long wasted waiting.**
> - ⛔ **Publishing location (hard - must land inside the target folder)**: the case page **must be directly under the target folder** - both app and cms cases land in the `{epic}-TestCase` folder (folder mode auto-ensures it under `{epic}`, sibling to `{epic}-Tech Solution`); **do not** hang it under the space "Overview" / personal space root (e.g. `4005004441`) or another page. The script writes the page directly into the resolved folder and **keeps it there on update** (verified: a published page reads back with `parentType: folder` and the target `parentId`), so the historical "update moves the page out to the space root" trap does not apply to this path. Still read back after publishing to confirm `parentId`, and if it is ever wrong, correct it immediately.
> - ⛔ **Every write goes through the script — a small change is not an exception (hard)**: there is **no** "incremental MCP edit" path any more. Even for a tiny change on an existing case page, **bump a new draft under `docs/`**, get user confirmation when the change is non-trivial, then rerun the upload script with the same `--title` prefix and folder mode args — the script dedupes onto that page and updates in place (`action: update`). **Never** call an Atlassian MCP page-write tool. If the local draft is gone, re-read the page with `getConfluencePage` (`contentFormat: markdown`), save under `docs/` as a new version, edit, confirm, republish. MCP **read-only** calls stay as before.
> - ⛔ **Duplicate Atlassian MCP (the Cursor Atlassian plugin)**: if the tool list shows **two** Jira / Confluence tool sets (`Atlassian-MCP-Server` plus a plugin-provided `*atlassian*` namespace), **ask the user to disable the Atlassian plugin in Cursor Settings → Plugins / Integrations** and keep only `Atlassian-MCP-Server`. Until it is disabled, use `Atlassian-MCP-Server` for all Jira reads/writes and Confluence reads, and treat every plugin page-write tool as forbidden.

## ⛔ Requirement-clarification gate (must do before generating cases - cannot be skipped)

After completing requirement pulling, page-fact search, frontend/backend scope analysis, and historical-defect/regression identification (workflow steps 2-6), **stop to clarify the requirement with the user before generating cases**. Purpose: confirm both "whether the involved pages are complete" and "the ambiguous points in the requirement", avoiding producing cases based on wrong/incomplete understanding. - Based on requirement analysis + page-fact search results, list to the user the **target pages this requirement involves** (align to existing page_doc slugs where possible, e.g. `property_list_page` / `review_booking_page`; write "to be collected" for missing docs). **Step 2 - Progressively question the requirement's ambiguities (one group at a time, clarify a batch before the next)**

- Collect the requirement's **ambiguities / vagueness / missing info** into a list; typical sources: unclear AC, undefined field optional/required, undescribed state (empty/error/loading) behavior, user-type/permission differences, boundaries and exceptions, uncertain backend interface/data rules, multi-platform consistency expectations, etc.
- **Ask in batches, progressively**: throw only a small group (suggested <=3) of the most critical questions at a time, ask the next group after the user answers, **do not pile up all questions at once**. For each question, give "your inferred default answer/inference" for the user to confirm or correct quickly.
- For details only **R&D knows** (backend/interface), if the user is also unsure, mark on the spot as "⚠️ needs R&D confirmation", **do not block** the flow, continue clarifying the rest.
- ⛔ **All clarification uses dialogs (hard)**: both step 1 "is the target page/module list missing anything" and step 2 "progressive questioning" **must use `AskQuestion` structured dialogs for the user to pick** (>=2 options per question, recommended option first and marked "(Recommended)", make "my inferred default answer" the first option, use `allow_multiple` where complex), **do not just list questions in the body as text for the user to type answers**.

    5. **Test Steps (操作步骤)** - **numbered one by one, written from the user-action perspective (open / click / enter / select …), in real admin-operation order, clear enough to reproduce without guessing; NO XPath/locators** (describe the menu / tab / button / field label the user sees, in-admin Chinese labels kept verbatim). ⛔ **Minimum detail bar (hard, aligned with the reference file `references/cms-case-template.md` § 2)**: (a) the first step(s) must state the **navigation entry point** - the exact sidebar menu / collection / tab / page the tester opens to reach the screen under test (e.g. "在左侧导航点击"内容管理 > 活动内容页"，打开列表页"); never start mid-screen; (b) one concrete action per step naming **action verb + exact on-screen target (quoted verbatim label) + concrete input/selection** (e.g. "在"音频标题"输入框输入…并点击"保存草稿""), not "配置标题"; (c) **spell out concrete data** - the actual text / exact file name+format+size / exact count; for a boundary test state both the exact at-limit and over-limit value AND the trigger action (blur / 保存草稿 / 提交审核); (d) a **functional/flow case needs ≥ 3 steps** (entry → operation → commit/verify); a pure single-field boundary case may be shorter but still needs the entry step + trigger action; (e) ⛔ **terse steps like "1. 输30字存；2. 输第31字" are rejected** - expand them. ⚠️ Before writing cases, read the reference file `references/cms-case-template.md` § 2 (minimum detail bar + bad-vs-good example) and match that level of detail.
    6. **Expected Result (预期结果)** - **numbered per point, corresponding to the steps**, each line an observable outcome
    7. **Pass/Fail (是否通过)** - left blank at authoring, filled Pass / Fail / Blocked at execution
    8. **Tester (测试实施者)** - left blank at authoring, filled at execution
    9. **Test Date (测试时间)** - left blank at authoring, filled at execution
    10. **Notes (备注)** - reason for any uncertain item + any uncovered requirement point + any module-fact gap ("to be captured")

     - **summary** = the case's **Function Point** (one-line title; keep it English per the title language constraint, Jira Key / proper nouns verbatim).
     - **description** = three labelled blocks mirroring GCD-469 exactly - **前置条件 (Preconditions)** / **操作步骤 (Test Steps)** / **预期结果 (Expected Result)** - filled from that row's Preconditions / Test Steps / Expected Result cells (numbered steps preserved; English narrative with quoted in-admin Chinese labels, same as the table).
