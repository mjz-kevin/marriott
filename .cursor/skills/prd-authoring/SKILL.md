# PRD Authoring（需求文档撰写）

基于已放行的澄清结论，按PRD模板撰写 PRD，交 PO 确认后进入发布环节。

| 维度 | 说明 |
|------|------|
| 定位 | 将澄清结论落成结构完整、目标可量化、AC 可测的 PRD |
| 输入 | 需求澄清结论（必填）、Figma 、历史 PRD/Epic、团队知识库 |
| 产出 | 符合模板的 PRD 文件 + 待确认清单 |
| 边界 | 只写 what 与 why，how 属技术方案环节；待确认清单不入正文、不发布 |

模板、文件命名、范围拆分维度、界面状态、内容模型要求、AC 书写格式、语言等均取自配置。

## 1. 前置条件


| #    | 条件                            |
| ---- | ------------------------------- |
| 1    | 需求澄清已放行：**P0 全部闭合** |


第 1 条不满足时回到需求澄清环节。**不得为赶进度跳过澄清**，PRD 返工成本远高于澄清一轮。

## 2. 输入


| 输入            | 必需 | 说明                                                        |
| --------------- | ---- | ----------------------------------------------------------- |
| 需求澄清结论    | 必填 | 事实来源                                                    |
| Figma           | 按需 | 提供链接时经 Figma MCP 读取，作为 UI Overview、功能模块表、Story 设计稿的依据 |
| 历史 PRD / Epic | 可选 | 术语与写法一致性                                            |
| 团队知识库      | 可选 | 既有业务规则与约束                                          |


## 3. 工作流

```
- S1  载入 prd-template.md
- S2  收集并通读输入
- S3  写 1. Business Overview
- S4  写 1.3 Scope
- S5  写 2. Feature Explanation
- S6  写 3. User Story List
- S7  写 4–10 章
- S8  [条件] 内容模型
- S9  补附录与待确认清单
- S10 自检
- S11 交 PO 确认
```

### S1 载入需求文档模板

读 [prd-template.md](references/prd-template.md)，以它的章节顺序与标题为基准，
（可选）/ 必填标注照抄，不自行增删章节、不改标题；模板里的 `{占位符}` 全部替换，不留残留。
不涉及的内容写「本期不涉及」，不删章节。

### S2 收集并通读输入

澄清结论是事实来源；里面的假设若被采纳，写入对应章节并标 `[假设]`。

输入含 Figma 链接时，**必须**通过 Figma MCP（`figma` server）读取设计内容——画板结构、界面状态、关键组件与字段、文案与交互标注——作为 UI Overview、功能模块表、Story 设计稿的事实依据，不基于链接推测。读取失败（无权限 / 链接失效 / MCP 不可用）时，将相关内容登记入待确认清单，不臆造设计细节。

### S3 写 1. Business Overview

- 1.1 Background：现状问题 → 业务影响 → 为什么现在做
- 1.2 Purpose：每条目标给全 当前值 → 目标值 → 度量方式 → 度量时间点，
仅写「提升效率」将被打回

### S4 写 1.3 Scope

按团队配置的范围拆分维度拆分，没涉及的维度写「本期不涉及」；优先级只用 P1 / P2。

### S5 写 2. Feature Explanation

- 2.1 产品架构图：用 mermaid 绘制，**必须遵守下方「图表规范」**，保证本地与发布后都能渲染
- 2.2 User Journey（含流程图，同样遵守「图表规范」）
- 2.3 UI Overview：给出设计稿与 Figma link，并依据 S2 读取的 Figma 事实标注设计稿定义的各界面状态（如加载/空/错误）；设计稿缺失的状态登记入待确认清单，不判定为「无此状态」
- 2.4 功能模块表：按 UI Section 逐张表，每行一个元素；
Operation Logic 写「用户操作 → 系统响应」不写实现；Data Requirement 写字段名与校验；
Performance Requirement 必须可量化（指标名 + 阈值 + 测量条件），不接受「快」「流畅」等模糊描述

### S6 写 3. User Story List

候选清单，句式 `As a {角色}, for {场景}, I want to {动作}, so that {价值}.`；
AC 按团队配置的书写格式写，能落到测试用例。最终 Story 以后续 User Story 撰写环节为准。

### S7 写 4–10 章

NFR 逐项给量化口径（性能、兼容性、离线与可用性、安全、可访问性）；安全按最小权限，
写清数据分级与日志留存；再写业务规则与约束、数据需求、依赖项、风险与待定项、优先级排序。

### S8 [条件] 内容模型

团队配置要求时加内容模型章，回答变更类型、历史内容影响、迁移与回滚，再补角色矩阵；
配置要求独立成条时，在 Story List 里拆成独立条目便于单独回滚。

### S9 补附录（待确认项不入正文）

填附录的 Figma / Jira 链接与术语表。**附录各链接字段有值则填、无值留空**，不写「由 XX 回填」「待补」等说明性文字。
**待确认清单不写入 PRD 文档正文，也不发布到 Confluence**；待确认项只在 S11 交付时于对话里逐条列出（含责任方）。

### S10 自检

按第 5 节质量门禁逐项过一遍。

### S11 交 PO 确认

在**对话里**给出产物与待确认清单（逐条标注责任方，仅存在于对话、不写入文档），说明下一步是进入 PRD 发布环节（等 PO 确认后）。**撰写完成后停下等 PO 确认，不自动进入下一环节**。

## 4. 强制规则


| 规则            | 说明                                                   |
| ------------- | ---------------------------------------------------- |
| 模板优先          | 章节顺序、标题、（可选）/ 必填标注一律以 prd-template.md 为准                 |
| 假设显式化         | 澄清结论里的假设若被采纳，写入对应章节并标 `[假设]`                         |
| 只写 what 与 why | how 交给后续的技术方案环节（Epic 级与 Story 级明细） |
| 目标可量化         | Purpose 与 Performance Requirement 必须有数字、口径与测量条件      |
| 常量不写死         | 模板、命名、维度、状态、语言一律取团队配置，禁止在产物里硬编码团队标识                  |
| 图表可渲染         | 所有 mermaid 图必须遵守下方「图表规范」，本地与发布后都能正常显示                |


### 图表规范

产出任何 mermaid 图（架构图、流程图、时序图等）时，逐条遵守：

1. **节点文本一律用双引号包裹**：`A["MBY Audio H5 页面"]`。含空格、括号、斜杠、中英文混排、标点的文本不加引号会触发 Lexical error。
2. **禁止在节点文本里用 `<br/>` 等 HTML 标签**换行。需要分行时，把补充信息拆到括号里或另起节点，例如 `E["Audio Playlist (新增: 章节列表)"]`。
3. **边标签也要加引号**：`E -->|"选择章节"| F`。
4. **节点 ID 用 ASCII**（`A`/`B`/`S1`），中文只放在带引号的显示文本里。
5. 写完自检：把图放进支持 mermaid 的预览器（或 mermaid live）确认无语法错误。
6. **若 Confluence 无Mermaid 插件**：发布环节会把图渲染成 PNG 图片附件嵌入。本地 `.md` 仍保留 mermaid 源码，二者内容需一致。

## 5. 质量门禁

- 与 prd-template.md 逐节对照：章节齐全、顺序一致、无空章节
- 无 `[填写]` / `TBD` / `TODO` 残留
- 目标可量化；AC 无模糊词，能落到测试用例
- 示例数据全是合成数据，无真实密钥、内网域名、真实会员号
- 同一概念全文使用统一名称
- 多语言字段写明缺翻译时的回退策略
- 所有 mermaid 图通过「图表规范」自检

细节见 [quality-gates.md](references/quality-gates.md)。

## 6. 输出

1. 产物文件，命名按团队的需求文档命名规则；结构与标题必须与 prd-template.md 一致，
    模板里的 `{占位符}` 全部替换、不留残留
2. 待确认清单，逐条标注责任方（**仅在对话中呈现，不写入产物文件、不发布**）
3. 下一步建议：PRD 发布环节（PO 确认后）
