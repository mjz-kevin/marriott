# Requirement Clarify（需求澄清）

在动笔写 PRD 之前，多轮澄清业务需求或方案分歧点。

**核心判断**：本 Skill 不产出文档。产出是会话里的澄清结论，回答三个问题：还缺什么、哪些地方自相矛盾、在没问清的部分我们暂定按什么假设走。
结论不落盘、不发布，直接作为 `prd-authoring` 的输入。

## 何时使用

| 用户输入 | 动作 |
|----------|------|
| 一段口述需求 / 会议纪要 / 一句话想法 | 全文检查 + 缺口扫描 |
| 「帮我看看这个需求还缺什么」 | 只做缺口扫描，输出清单 |
| 「按这个需求写 PRD」 | 先走本 Skill，P0 全部闭合再转撰写 |
| 已有 PRD 草稿，想查漏 | 以 PRD 为输入做反向扫描 |

**不适用**：需求已经明确到可以直接填模板（此时直接进 `prd-authoring`）。

## 输入

| 输入 | 必需 | 说明 |
|------|------|------|
| 原始需求 / 纪要 | 必填 | 文本、链接、口述转写均可 |
| Figma 链接 | 可选 | 有则先提取视觉事实并入上下文 |
| 关联 Jira / Confluence | 可选 | 读历史需求文档、Epic、既有 Story 做上下文 |

## 工作流

```
1. 收集输入并按维度清单扫描缺口
2. 检测冲突
3. 批量提问（P0 优先）
4. 未闭合项落成假设 / 待确认，给出澄清结论
```

不要在第一轮就要求用户把信息整理好——整理是本 Skill 的职责。并行读取原始需求、关联的 Jira/Confluence、Figma（若有）。

### 1. 扫描缺口

逐维过下面的清单，判定 `COVERED / PARTIAL / MISSING`。**必须逐维过一遍，不能凭感觉挑几个问。**

| 维度 | COVERED 判据 | 常见 MISSING 表现 |
|------|--------------|-------------------|
| 问题陈述 | 谁的什么问题、现在怎么解决、代价是什么 | 只有"做一个 XX 功能" |
| 目标与度量 | 1–3 条可量化目标，含当前值与目标值 | "提升效率""优化体验" |
| 范围与边界 | 明确 in/out-of-scope，按端拆分 | 没说做不做 Android / 后台 |
| 角色与场景 | 角色 × 场景，覆盖主路径与异常路径 | 只有 happy path |
| 业务流程 | 分步流程，含触发条件与系统处理逻辑 | 只有界面没有流程 |
| 界面与状态 | 有设计稿，default/loading/empty/error 齐全 | 只有 default 态 |
| 数据与规则 | 字段、来源、校验、默认值、异常处理 | 只有字段列表 |
| 集成与依赖 | 上下游系统、负责人、状态 | 默认"接口都有" |
| 非功能 / 安全合规 | 性能容量可用性有量化口径；权限、审计、数据分级明确 | 空白或只写"遵循规范" |
| 验收标准 | 可观察、可自动化、覆盖正反例与边界 | "功能正常""体验良好" |

### 2. 检测冲突

至少查三类，找到即列给用户裁决，**AI 不自行选边**：

| 冲突类型 | 例子 |
|----------|------|
| 自相矛盾 | 需求说"所有用户可见"，AC 里又写"仅会员可见" |
| 度量冲突 | 目标"减少操作步骤"，方案却增加一步确认弹窗 |
| 约束冲突 | "首屏 1 秒加载" + "首屏展示 8 个实时接口" |

### 3. 批量提问

先给问题分级，再一次输出完整清单，**禁止一问一答挤牙膏**：

| 级别 | 含义 | 处理 |
|------|------|------|
| **P0 阻塞** | 答案不同会导致方案完全不同或返工 | 必须回答，未闭合不得进入下一环节 |
| **P1 影响范围** | 影响工作量与排期，不改变方向 | 给推荐默认值，用户可沿用 |
| **P2 可假设** | 有行业通行做法 | 直接登记为假设，用户可事后推翻 |

每轮 P0 ≤ 5 个，P0 + P1 ≤ 8 个，超出分批先问 P0。每个问题用四要素格式：

```markdown
### Q{n} · [{P0|P1|P2}] · {维度}
**问题**：{一句话，闭合式优先}
**为什么问**：{这个答案会改变什么}
**推荐默认**：{默认取值}（若无异议即按此执行）
**选项**：A. … B. … C. … （或「其他：___」）
```

禁止：只给默认值就不问（把判断题变填空题）、问「你还有什么补充」这类无信息量问题、把 P2 包装成 P0 逼用户回答。

### 4. 假设登记与澄清结论

凡是没问到、没答清、或用户选了默认值的项，全部登记。假设不是免责声明，每条写清「推翻成本」，让用户判断值不值得现在确认。

在对话里直接给出下面这段结论（不写文件、不发布），它就是交给 `prd-authoring` 的输入：

```markdown
## 1. 已确认结论
{按维度列出，每条一句话，标注来源：原始需求 / 第 n 轮回答 / 设计稿 / 代码事实}

## 2. 冲突与裁决
| 冲突 | 选项 | 裁决 | 裁决人 |

## 3. 待确认（P0 未闭合，无则写「无」）

## 4. 假设登记
| # | 假设 | 依据 | 影响面 | 推翻成本 |

## 5. 下一步
→ P0 全部闭合：直接进 prd-authoring，上面这段即其输入
→ 否则：继续下一轮，或退回需求方补齐
```

## 收敛规则

- **轮次上限 3 轮**。第 1 轮扫全部维度出缺口清单，第 2 轮对上轮回答做二次扫描（新答案常引入新缺口），第 3 轮只问仍未闭合的 P0 并给假设登记。第 4 轮起**停止提问**，把未决项写成风险表交人工确认。超过 3 轮说明输入质量本身有问题，应退回需求方。
- **放行门槛**：P0 全部闭合才放行到 `prd-authoring`；仍有 P0 未闭合则不放行，无论其它维度多齐。若维度大面上齐了但个别非 P0 项待定，可放行但要求 PRD 保留「待确认」章节。
- **每个问题必须带推荐默认值**。
- **不臆造业务规则**。没查到也没问到的一律进假设登记，不能写进「已确认结论」。
- **区分事实与推断**。来自代码/文档/原话的标来源；AI 推断的显式标注。
- **敏感信息不过问也不记录**。遇到手机号、账号等真实数据，只确认「是否需要该字段」，不记录值。

## 质量门禁

调用 `references/quality-gates.md`。澄清结论的最低要求：每个维度都有判定、假设表非空（或有显式「无假设」）、待确认项全部标注责任方。

## 输出示例

```markdown
**轮次**：2/3

## 已确认结论
- 问题陈述：会员无法在一个入口看到全部可用权益（来源：原始需求第 1 段）
- 目标：权益页转化率从 12% 提升到 18%（来源：第 2 轮回答）

## 冲突与裁决
| 冲突 | 选项 | 裁决 |
| 「所有用户可见」vs「仅会员可见」 | A 全量 B 会员 | 待 PO 裁决 |

## 待确认（P0）
- Q3 是否包含 Android 端？

## 假设登记
| # | 假设 | 依据 | 推翻成本 |
| A1 | 首期只做 iOS | 范围表只勾了 iOS | 低：补一份 Scope |

## 下一步
→ P0 未闭合（Q3），暂不放行。请先回答 Q3。
```

用户答完 Q3 后继续下一轮，P0 全部闭合后直接进 `prd-authoring`。
