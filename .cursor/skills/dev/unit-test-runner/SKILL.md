# unit-test-runner — running unit tests and summarizing pass rate and coverage

Run the team-declared unit-test commands on the current Feature branch, give a "pass / fail" conclusion, and summarize the pass rate, failed cases, and coverage. It's a runner; it doesn't generate cases (cases are generated by the development step).

| Dimension | Description |
|------|------|
| Purpose | Run the unit-test commands, summarize pass rate / failed cases / coverage, rule against the threshold |
| Input | The Feature branch's implementation code + unit-test code + the team test config |
| Output | A unit-test conclusion (pass / fail) + pass rate + failed-case list + coverage |
| Scope | Only runs and tallies; doesn't write/change unit tests, doesn't change business code |

## 0. Config values

`{profile}` is the current profile file name (without extension, e.g. `app-prod` / `cms-test`), resolved and passed in by the caller via the profile-selection step (`profile.py resolve` gives its absolute path); if it is not passed in or the file does not exist → stop, don't guess.

| Purpose | Config key |
|------|----|
| Test tool | `profiles/{profile}.yaml` → `test.unit.*.tool` (`gradle` / `xcodebuild` / `pnpm` / `pnpm-nx`) — determines how to assemble the command |
| Test semantics | The semantic fields under `profiles/{profile}.yaml` → `test.unit.*`: gradle uses `tasks`; single-shell xcodebuild uses `project`/`scheme`/`destination`/`only_testing`, modular uses `test_style: spm_module_scheme` + `modules_discovery` (`glob`/`scheme_from`/`test_target`/`include_if`/`package_dir`, derived by scanning packages at runtime, no hand-written module table); pnpm uses `script`; pnpm-nx uses `nx.{command,targets,base_ref,head_ref}` — selected by the end / repo under test (APP: `ios` / `android`; CMS: `cncms` / `monorepo`) |
| Coverage threshold | `profiles/{profile}.yaml` → `test.coverage` (`enabled` decides whether to tally and show coverage; `min_line` decides whether to gate: `min_line=0` reports only without gating, `min_line>0` rules a fail below the threshold. The two fields have orthogonal responsibilities) |

Required config keys missing (TBD) → stop and ask for them; don't guess the test command.

**Command assembly (cross-OS)**: this skill doesn't take a ready-made command string from the profile; it assembles the command at runtime from `tool` and the semantic fields, adapting to the current OS:

| tool | Assembly | Key point |
|------|------|------|
| `gradle` | `<wrapper> <tasks...>` | pick the wrapper by OS: `gradlew.bat` (Windows) / `./gradlew` (Unix/macOS) |
| `xcodebuild` | Single shell: `xcodebuild test -project {project} -scheme {scheme} -destination '{destination}' -only-testing:{only_testing}`; modular (`test_style: spm_module_scheme`): inside the module under test's `package_dir`, `xcodebuild test -scheme {scheme} -destination '{destination}' -only-testing:{test_target}/{test class}` | macOS only; `{simulator}` is substituted with an available local simulator (pick one via `xcrun simctl list devices available`). When modular, derive the module list by scanning `Package.swift` per `modules_discovery` (don't read a hand-written table), then select by the modules this change touches and run only the relevant ones |
| `pnpm` | `pnpm run {script}` | consistent cross-platform |
| `pnpm-nx` | `pnpm exec nx {nx.command} -t {nx.targets...} --base <sha> --head {nx.head_ref}` | **The value of `--base` is first obtained in two steps: ① run `git merge-base HEAD {nx.base_ref}` (substituting `{base}` in `base_ref` with `repos.*.base` first) to get the SHA; ② pass the SHA as `--base`. Don't use `$(...)` command substitution (Windows doesn't support it)** |

## 1. Prerequisites

| # | Condition |
|---|------|
| 1 | On the Feature branch under verification, with the implementation code + unit-test code in place |
| 2 | The build has passed (unit tests can't run reliably when compilation fails; fix the build first) |
| 3 | The unique unit-test command and coverage spec can be resolved per end / repo |
| 4 | The repo's local working directory is provided by the caller at runtime (unit tests run inside it) |
| 5 | The test runtime environment is ready: iOS needs an available simulator + local Dependencies ready (not SPM auto-fetch); for cncms etc., if `test.unit.*.needs_services` (e.g. postgres/redis) is configured, the dependent services must be up first (e.g. `docker compose up -d`). An environment not ready is an environment issue, not a code failure |

## 2. Workflow

```
- S1 Assemble the unit-test command from the tool and semantic fields, combined with the current OS (including step-by-step resolution of the monorepo base SHA)
- S2 Run the unit tests, fully capturing the output
- S3 Summarize the pass rate, failed-case list, and coverage
- S4 Rule pass or fail against the coverage threshold (min_line)
- S5 Report the conclusion: pass → proceed / fail → send back to the development step
```

### S1 Assemble the command (cross-OS)

Assemble the command from `test.unit.*.tool` and the semantic fields (see the assembly table in "0. Config values"), adapting to the current OS: pick the gradle wrapper by OS, `gradlew.bat`/`./gradlew`; xcodebuild is macOS only and `{simulator}` is substituted with an available local simulator. **iOS modular (`test_style: spm_module_scheme`)**: this repo's unit tests are spread across SPM modules (the main-shell target is only a placeholder, don't use it). The module list isn't maintained by hand; derive it at runtime per `modules_discovery` — scan each `Package.swift` via `glob`, take `scheme` from the file's `packageName` (the directory name ≠ the package name, so the file must be read), `test_target` = `{scheme}Tests`, `package_dir` = the directory the glob hits, and include only modules that declare a `.testTarget` (`include_if: has_test_target`). Then select from the derived list by the modules this change touches, run `xcodebuild test -scheme {scheme}` inside their `package_dir`, with `-only-testing` scoped to this change's `{test_target}/{test class}`, running only the relevant modules rather than everything. **monorepo (pnpm-nx affected) first obtains the comparison base in two steps**: ① substitute `{base}` in `nx.base_ref` with `repos.*.base`, run `git merge-base HEAD {base_ref}` to get the SHA; ② pass that SHA as `--base`. Don't use `$(...)` command substitution (Windows doesn't support it).

### S2 Run the unit tests

Run the command assembled in S1, fully capturing the output. Unit tests usually take a while, so allow enough timeout and keep the full log for locating failed cases, don't truncate.

### S3 Summarize

Summarize from the test output:

| Summary item | Content |
|------|------|
| Pass rate | passed / total (with skipped listed separately) |
| Failed cases | case name + failing assertion/error message + file |
| Coverage | line coverage (tallied and shown when `coverage.enabled` is true) |

### S4 Threshold ruling

The two coverage fields have orthogonal responsibilities: `enabled` only decides whether to tally and show coverage, `min_line` only decides whether to gate.

| Conclusion | Criteria |
|------|------|
| Pass | All cases pass, and (when `min_line>0`) line coverage ≥ `min_line` |
| Fail | There are failed cases, or `min_line>0` and line coverage < `min_line` |

When `min_line=0`, regardless of `enabled`, coverage is reported only and doesn't gate (pass/fail depends only on the cases).
When coverage is short but all cases pass, clearly distinguish "case failure" from "insufficient coverage" — the two have different fix actions.

## 3. Mandatory rules

| Rule | Description |
|------|------|
| Assemble the command semantically | Assemble the command from `tool` + semantic fields, don't take a ready-made command string from the profile |
| Cross-OS adaptation | Pick the gradle wrapper by OS; obtain the monorepo base SHA in two steps (`git merge-base` then pass `--base`), don't use `$(...)`; xcodebuild is macOS only |
| Run only, don't change | Don't write/change unit tests or business code; record missing or unreasonable cases as findings and hand upstream |
| Threshold follows config | Whether to gate depends only on `min_line` (`min_line=0` reports only without gating, `min_line>0` rules a fail below the threshold); `enabled` only decides whether to tally and show coverage |
| Distinguish failure types | Distinguish "case failure" from "insufficient coverage", giving each a fix direction |
| Don't misjudge environment issues | An unavailable test environment (simulator/dependency) is an environment issue, not a code failure |
| Respect the retry limit | The self-loop carries a retry limit; past the limit, prompt for human intervention |

## 4. Quality gates

- The command and coverage spec were assembled from the team-configured `tool` + semantic fields (not guessed, not a ready-made command string)
- The conclusion is explicitly pass / fail, with pass rate + failed cases + coverage attached
- Coverage is gated by `min_line` (`min_line=0` reports only, `min_line>0` gates against the threshold); `enabled` decides whether to tally and show
- "Case failure" and "insufficient coverage" are distinguished, each with a fix direction
- Give an explicit next step among "proceed / send back / prompt for human"

## 5. Output

```markdown
Unit tests: {repo} / {framework} — {Pass | Fail}

- **Pass rate**: {pass}/{total} (skipped {skip})
- **Line coverage**: {cov}% (threshold min_line={min})

|------|------|------|
```

## 6. Troubleshooting

| Symptom | Handling |
|------|------|
| The test environment is unavailable | Report as an environment issue, don't rule a code failure, don't send back |
| Compilation hasn't passed | Fix the build first, defer the unit tests |
| Can't resolve the unit-test command | Stop; state the missing config key and the owner to supply it |
| All cases pass but coverage is short | Rule a fail and note it's insufficient coverage; hand upstream to add tests rather than change business code |
| Repeated failures beyond the retry limit | Prompt for human intervention, don't send back endlessly |
| Unit tests can't run at all because "another test file" fails to compile (common to iOS/Android) | An XCTest test target and a gradle test source set both compile **as a whole**: any one test file in the same target failing to compile (common when production code changed but old unit tests weren't synced) fails the whole unit-test task, and even if `-only-testing` specifies a single class, the whole target compiles first. Report it as "test target compile failure" and list the uncompilable test files for the development step to sync-fix; don't rule it a failure of the code under test. iOS example: `type 'X' has no member 'Y'` from a stale broken test in the same target |
| iOS main-shell `DragonAppTests` doesn't hit the real unit tests | The main-shell target is only a placeholder; the real unit tests are in each SPM module's `Module/ios-dragon-*/Tests/`. Run the module scheme derived via `modules_discovery` per `test_style: spm_module_scheme`, don't run the main shell |
| iOS bare `swift test` reports `no library for this platform` | The module depends on an xcframework with an iOS-only slice, so macOS compilation fails. Use `xcodebuild test -destination 'platform=iOS Simulator'` (the module scheme), not bare `swift test`. It's an inherent constraint, not a code failure |
| Inside the agent sandbox, iOS xcodebuild can't reach the simulator service (`CoreSimulatorService connection became invalid` / `Operation not permitted` / `Unable to discover any Simulator runtimes`) | The agent's default command sandbox intercepts access to CoreSimulatorService, DerivedData, the SPM cache, etc., so `xcodebuild`/`simctl` can't start. It's a sandbox-environment limitation, not a code failure: it must be **run outside the sandbox** (lift the command sandbox / grant full permissions) and re-run, don't rule a unit-test failure or send back based on this |
| Android environment/secret prerequisites (same as build-verify) | Unit tests likewise depend on JDK 17, the repo-root `secret_android_api_keys.json`, and private-repo credentials; if missing, it's an environment/credential issue, not a code failure |
| Android public dependency download fails / `--offline` has no cache (same as build-verify) | In a restricted execution environment (agent sandbox), Gradle(JDK)'s outbound TLS is intercepted, and unit tests going online for dependencies likewise fail with `SSLHandshakeException: protocol_version`. Per build-verify's offline convention: warm up `~/.gradle` in a normal terminal first, then on the agent use `GRADLE_USER_HOME=$HOME/.gradle ./gradlew <unit-test tasks> --offline`. It's an environment issue, not a code failure |
