# Tech Solution — Detail 级（Story 级详细设计）

Story 级明细技术方案，在开发启动前基于 User Story + AC 产出，是**唯一可供 DEV 直接照此实现**的一档，也是单测编写、接口契约比对、任务验收的比对基线。

| 维度 | 说明 |
|------|------|
| 定位 | 落到接口字段级的详细设计 + 任务拆解 + 每项任务验收标准 |
| 输入 | Story + AC、已确认的 Epic 档方案、设计稿（Figma 链接） |
| 产出 | 一份 Story 级明细方案（对齐团队 detail 模板），作为 feature 分支的关联任务清单与验证基线 |
| 边界 | 不改需求方向（方向变更回 Epic 级方案确认）；不估点，只给影响面与任务数；接口示例一律 mock 且必须含错误场景 |
| 验收基准 | 判断标准：一个不参与前期讨论的 DEV，看完能不能直接开工 |

按团队所用的 detail 模板自带的章节顺序逐章填，不增删章节、不与其他模板混用。

## 0. 配置取值

`{profile}` 为当前 profile 文件名（不含扩展名，如 `app-prod` / `cms-test`），由调用方通过 `profile-select` skill 解析并传入（`profile.py resolve` 给出其绝对路径）；未传入或对应文件不存在 → 阻断，不猜测。

| 用途 | 键 |
|------|----|
| 是否要内容模型 | `profiles/{profile}.yaml` → `content_model.required` |
| 代码仓库默认分支 | `profiles/{profile}.yaml` → `mcp.github.default_branch` |
| detail 模板 | `profiles/{profile}.yaml` → `artifacts.user_story_template` 同源目录下的 detail 模板（app / cms 各一份） |

## 1. 前置条件

| # | 条件 |
|---|------|
| 1 | 有 Story + AC（验收边界） |
| 2 | Epic 档方案已确认（方向不变，否则先回 Epic 级方案确认） |
| 3 | 有设计稿（Figma 链接），覆盖设计稿定义的界面状态 |

## 2. 工作流

```
- S1 文档信息 + 版本变更记录
- S2 背景
- S3 主流程
- S4 契约与依赖
- S5 [条件] 内容模型 + 权限 + 迁移（团队要求内容模型时填）
- S6 任务拆解（每项含验收标准）
- S7 风险与依赖
- S8 专项章节（可复用组件、QA 测试路径、监控、非功能设计等）
- S9 评审结论
- S10 自检 + 交 DEV 确认

具体章节名与编号以所用模板为准。
```

### S3 主流程

按模板的主流程章节填写：入口、请求时机、数据加载、业务异常、状态切换、关键操作后跳转，
并附流程图或架构图。

### S4 契约与依赖

**接口 / 数据契约**必须写清四件事：

| 项 | 要求 |
|----|------|
| 请求 / 触发时机 | 进页 / 刷新 / 登录态变化 |
| 关键字段 | `字段名`：含义、类型 |
| 空值 / 失败兜底 | 字段为空→？请求失败→兜底策略，**不静默失败** |
| 前置 / Safelisting | 接口 safelist |

给出**请求 / 响应 / 错误码**的 mock 示例（策略按团队的示例数据口径，
域名 `api.example.com`），**必须含错误场景**，只给成功示例的方案无法验收。

**Feature Flag / 配置项**表逐行填：Key、含义、默认值、**读取失败时的行为**、备注。
> 默认值默认「关」，读取失败不阻塞进页，两端读同一 key，不本地写死默认开。

**设计 / 规格来源**必须给出 Figma 链接。

### S5 内容模型三张关键表（团队要求内容模型时必填）

**内容模型**：内容类型 / 用途 / 关键字段 / 草稿·版本 / **多语言**（是否多语言 + 回退策略）

**权限与发布流程**：editor / reviewer / admin 的读写发布矩阵 + 发布流程（draft → 审核 → published，驳回如何处理）

**数据迁移**：

| 变更类型 | 对象 | 说明 | 迁移方式 |
|----------|------|------|----------|
| 新增 / 删除 / 改类型 / 改名 | `[collection.field]` | | `payload migrate`（生成 + 执行迁移脚本） |

必须回答**历史内容影响**（存量是否回填）与**回滚脚本**。
当 团队要求内容模型独立成条，迁移应作为独立任务项并可独立回滚。

### S6 任务拆解

| 项 | 技术任务 | 其他 Comments |
|----|----------|---------------|

**每个任务必须有验收标准**（可写在 Comments 或单独列）。
这是任务验收环节的比对基线，缺一项，验证环节就无法执行。
任务应可独立验收、粒度不宜过大（过大则继续拆）；工时/点数由 DEV 评估。

### S8 专项章节

按模板的专项章节逐项填：

| 要点 | 内容 |
|------|------|
| 可复用组件 | 组件名 / 使用处；优先复用设计系统组件（见团队的编码约定） |
| 多端 / 多站点差异 | 逐需求点列出差异，无差异写「一致」 |
| 建议 QA 测试路径 | 覆盖团队的测试范围；状态覆盖设计稿定义的界面状态逐态 |
| 上线后监控 | 埋点、崩溃 / 性能指标、发布成功率 |
| 非功能设计 | 性能、缓存（TTL 与失效）、安全（鉴权、越权防护） |
| 其他 | 状态页（Loading / Empty / Error）与边界 |

## 3. 强制规则

| 规则 | 说明 |
|------|------|
| 接口示例必须 mock | 禁真实密钥、内网域名、会员号 |
| 示例含错误场景 | 只给成功示例无法验收 |
| 引用真实代码路径 | 引用前必须实际检索过相关代码仓库 |
| 任务都有验收标准 | 缺一项即打回 |
| 不估点 | 只给影响面与任务数 |
| 状态不遗漏 | 设计稿定义的界面状态每态都要有处理说明 |
| 章节不删除 | 不涉及写「本期不涉及」 |

## 4. 质量门禁

- 模板章节齐全，无空章节
- 无占位符残留
- 接口契约含请求/响应/错误码 mock，且写明空值与失败兜底
- Feature Flag 表含「读取失败时」行为
- 每个任务都有验收标准
- 未出现真实密钥 / 内网域名 / 真实会员号
- 专项章节已填：差异表、QA 测试路径覆盖全部 UI 状态、监控方式、非功能设计
- 团队要求内容模型时：内容模型表非空、权限矩阵已填、迁移表含回滚
- 多语言：按团队的多语言要求给了回退策略

## 5. 输出

命名按团队的标题格式。
交付后**停下等 DEV 确认**，确认后进入技术方案发布环节（detail 模式）。
