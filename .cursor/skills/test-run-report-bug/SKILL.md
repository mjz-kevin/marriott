# test-run-report-bug: pick platform -> run all features -> generate run report -> publish to Confluence (error cause on top) -> file Jira Bugs for failed cases

This skill handles "**first let the user pick a platform (iOS / Android / All / Custom) -> automatically run all features of that platform -> collect pytest run results -> analyze failure root causes -> publish as a Confluence page to the test_report folder (error cause on top) -> after the report is generated and root-cause analysis is complete, file corresponding Bugs on Jira for the failed cases**". It is a standalone stage outside the main line (authoring -> to-script -> debug), facing "execution + report + attribution + bug filing".

> ⛔ **Confluence / Jira content language constraint (hard, cannot be skipped)**: when publishing the run report to the [test_report folder](https://marriottcloud.atlassian.net/wiki/spaces/~712020dbd6441f05734e4da1386119f88cfbe0/folder/4261085398/test_report) and filing Jira Bugs for failed cases, **all content generated by this skill must be in English** - including the report page title, error-cause summary, section titles, table headers, root-cause analysis and fix suggestions, the Jira Bug's Summary / Description, etc. The only exception: **machine output quoted verbatim** from the test artifacts (exception type, traceback key lines, junitxml snippets, terminal output, feature/step original sentences, case names, etc.) are **kept verbatim, not translated** - they are real run evidence and rewriting them distorts. I.e. "narratives this skill writes itself are in English, while quoted machine/evidence text stays as-is".

> **Boundary**: this skill only does "execute, report, attribute, file bugs". It **does not modify** the pages/steps/features/conftest under `tests/mobile/{ios,android}/`; if the report shows code needs changing to fix a bug, hand it back to `test-debug-script` (this skill only gives root-cause judgments and suggestions in the report and files the failures as Jira Bug tickets).

## (1) Proactively ask for the run platform (gate, cannot be skipped)

The **first thing** after entering this skill is to use `AskQuestion` to let the user pick the run scope, with options at least including (recommended first and marked "(Recommended)"):

- **iOS (recommended)** - run **all features** registered in `tests/mobile/ios/plan/debug.py` (`--app-platform ios`).
- **Android** - run **all features** registered in `tests/mobile/android/plan/debug.py` (`--app-platform android`).
- **All (iOS + Android)** - run both platforms' `plan/debug.py` in turn.
- **Custom** - the user's custom run target (e.g. a single `features/<JIRA_KEY>.feature`, an added `-k`/`-m` with a marker registered in `pytest.ini`, or a specific platform+file).

After the pick, record "platform + run target file + extra params" as the report page's traceability info. **Do not guess which platform/file to run**; when the user picks "Custom" but gives no specific file, ask before running.

## (2) Run the script

- The run entry is the same for both platforms: run the corresponding platform's `plan/debug.py` (its `scenarios(...)` registers **all features** to run for that platform); the pytest option **`--app-platform ios|android`** decides which platform's env/conftest to load (**do not use `PLATFORM=...` env var** — it has no effect in this project). Markers only use those registered in `tests/pytest.ini`, **do not write `-m ios`/`-m android`** (unregistered).
- pytest already configures `--alluredir allure-results` in `tests/pytest.ini` (`--clean-alluredir` each time). **Add `--junitxml`** to stably parse stats and failure details without relying on the allure binary.

**iOS (run all iOS features)**:

```bash
source .venv/bin/activate
.venv/bin/python -m pytest tests/mobile/ios/plan/debug.py -v --app-platform ios \
  --junitxml=tests/mobile/ios/log/last_run_report.xml
```

**Android (run all Android features)**:

```bash
source .venv/bin/activate
.venv/bin/python -m pytest tests/mobile/android/plan/debug.py -v --app-platform android \
  --junitxml=tests/mobile/android/log/last_run_report.xml
```

**All (iOS + Android)**: run the two commands above in turn (each junitxml persisted separately), collecting results separately and attributing separately.

**Custom**: replace the target file in the commands above with the user-specified `features/<JIRA_KEY>.feature` or add the user's `-k`/`-m` (markers must be registered in `pytest.ini`), with `--app-platform` set to the user's chosen platform.

- Do an environment self-check before running (Appium `/status`, iOS with `xcrun devicectl list devices` and `.env.ios.lle` consistent with `plan/ios_test_config.py`, Android with `adb devices`); prompt the user first if not met, do not blindly run.
- Allow long duration: real-device cases run slowly, use a longer foreground wait and run in the background with progress polling when necessary; do not conclude before the run finishes.

## (3) Collect and analyze run results

**Collection sources (by priority)**:
1. `--junitxml` artifact (iOS: `tests/mobile/ios/log/last_run_report.xml`; Android: `tests/mobile/android/log/last_run_report.xml`): parse total / pass / fail / error / skip, and each testcase's `<failure>`/`<error>` message and traceback.
2. pytest terminal output (terminal file): failing step, `assert` context, pytest-bdd `Scenario`/`Step` location.
3. failure auto-screenshots under `screenshots/` (conftest saves on failure, named by case name) - **only as local human-investigation evidence, not written into the Confluence report body**.
4. raw results in `allure-results/` (view with `allure open` when finer granularity is needed, optional).

> When "All (iOS + Android)" is chosen, **collect and attribute per platform separately** (parse junitxml/terminal output separately), do not mix the two platforms into one stat.

**Root-cause analysis (this skill's core added value)**: for each failure/error, classify against the "common root cause" rules in `.cursor/profiles/test_script_memory.yaml`, producing a three-part output:

- **Root cause**: one sentence on why it failed (e.g. "asserted the previous page's control before the transition settled, caught a stale frame").
- **Matched rule**: point to the corresponding `RULE_00X` (if matched); against the "common root-cause cheat sheet" below.
- **Fix suggestion**: the minimal-change direction (which locator / wait strategy / assertion normalization to change), noting "code fix is taken by `test-debug-script`".

When the root cause cannot be judged from evidence, mark "root cause pending re-check" and state what evidence is still missing (e.g. "need the real device left on that page to verify elements"), **do not fabricate the root cause**.

### Common root-cause cheat sheet (against test_script_memory.yaml)

| Exception/symptom | Likely root cause | Rule |
|-----------|--------------|----------|
| `TimeoutException` stuck long on a page | implicit+explicit wait stacking / hard sleep / idle slowdown | RULE_005 / RULE_001 / RULE_018 / RULE_020 |
| `NoSuchElementException` cannot locate | locator stale (with hash / deep xpath) / not scrolled into the visible area / name guessed wrong | RULE_002 / RULE_003 / RULE_015 / RULE_009 |
| `StaleElementReferenceException` / 'not present in current view' | the continuously-refreshing page element was rebuilt, reused an old reference | RULE_016 |
| `AssertionError` text unequal but looks identical | rendered spaces/format differences, assertion not normalized | RULE_008 |
| `AssertionError` assertion fails on a success page / caught a stale frame | asserted the previous page's control before the transition settled (race) | RULE_010 |
| Option/result matches a similar other one | used CONTAINS matching the longer, should BEGINSWITH/exact | RULE_013 |
| Tapped but did not navigate / click very slow | event not bound to the text/container or dragged down by waiting idle, should use coordinate mobile:tap | RULE_014 |
| Input box drops characters | one-shot send_keys too fast, should use per-character input | RULE_017 |
| `StepDefinitionNotFoundError` | the same step sentence uses different keywords but only @given is registered | RULE_019 |

## (4) Whole-page report structure (AI lays out the page accordingly - authored as Markdown, converted by the upload script; following `用例报告模板` pageId `4261053064`)

**⚠️ Hard constraint: the error-cause summary must go at the very top of the doc (the first section of the body, below the title and before everything else). The report body writes no images/screenshots; failure evidence is expressed in text only.**

- **Top: ⚠️ error-cause summary (pinned, appears first)**:
  - A one-sentence overall conclusion (e.g. "3 cases failed, 2 with the same cause: transition race; 1 locator stale").
  - List each failed case: `case/scenario name | failing step | exception type | root cause | matched rule | fix suggestion | Jira Bug` (table; the `Jira Bug` column is backfilled with the bug key + link after ticket creation in "(6) File Jira Bugs").
  - If all passed, write "all passed this run, no errors" in this section.
- **One, run overview**: run target file + extra params, run time, environment (device/BUNDLE_ID/account type), command line.
- **Two, result stats**: `total | pass | fail | error | skip | pass rate | total duration` (table).
- **Three, case details**: one row per testcase: `scenario/case | result | duration | failing step | exception summary`.
- **Four, failure details and traceback**: for each failure/error, paste the key traceback lines, failing step, pytest-bdd location (**plain text, no screenshots**).
- **Five, root-cause analysis and suggestions**: expand the three-part output (root cause / matched rule / fix suggestion) one by one; explicitly mark "hand to test-debug-script to fix" for those needing code changes.
- **Six, appendix**: junitxml path, allure-results note, raw terminal output snippet (truncated, keep the key part).

> The top summary and "five, root-cause analysis" have consistent content, but the top only puts a **refined conclusion + failure list**, convenient for seeing all error causes at a glance.

## (5) Publishing conventions (Confluence test_report folder)

**Artifact location**: the Confluence [test_report folder](https://marriottcloud.atlassian.net/wiki/spaces/~712020dbd6441f05734e4da1386119f88cfbe0/folder/4261085398/test_report) (folderId `4261085398`, same space as `test_case` / `page_doc`, space key `~712020dbd6441f05734e4da1386119f88cfbe0`, `spaceId 4005003910`, `cloudId 627b9bb1-1899-4ff6-bc6e-066cf136a066`). **One run produces one Confluence page**; the local Markdown report (`tests/mobile/<platform>/log/last_run_report.md`) is the publishing input and local traceability copy, alongside intermediate material like junitxml.

**Unified template (shared by iOS / Android)**: all run reports are **output following the layout and section structure of [`用例报告模板`](https://marriottcloud.atlassian.net/wiki/spaces/~712020dbd6441f05734e4da1386119f88cfbe0/pages/4261053064) (pageId `4261053064`)** - error-cause summary pinned + six sections (run overview / result stats / case details / failure details and traceback / root-cause analysis and suggestions / appendix). **The report body writes no images/screenshots**; failure evidence is expressed in text only (exception type, traceback key lines, failing step, root-cause analysis); the screenshot paths are only for local human viewing, not into the Confluence body.

**Page naming convention (traceability aligned with test_case titles such as `iOS Test Case - <JIRA_KEY> ...`; report titles use `<platform>` = iOS / Android)**:

- Run all features of a platform (default): **`<platform> 运行报告 - 全部用例 <YYYY-MM-DD HH:mm>`**, e.g. `iOS 运行报告 - 全部用例 2026-09-27 17:40`.
- Custom run of a single feature (with a Jira Key): **`<platform> 运行报告 - <JIRA_KEY> <YYYY-MM-DD HH:mm>`**, e.g. `iOS 运行报告 - CNAPP-383 2026-09-27 17:40`.
- **When "All (iOS + Android)" is chosen**: **one page per platform** (each title carries its own platform name), not merged; return each link to the user.
- The report carries a timestamp so multiple runs of the same platform/case leave a trace without overwriting each other (create a new one by default; only update when the user explicitly asks to "update the most recent").

**Publishing method (the report body goes through the shared Confluence upload script; Jira/dedupe/read-back go through `Atlassian-MCP-Server`, `cloudId` `627b9bb1-1899-4ff6-bc6e-066cf136a066`)**:

1. First dedupe in the test_report folder (`getConfluencePageDescendants` to list folder children / `searchConfluenceUsingCql` to search by title) to see whether a report for this run already exists.
2. Write the report body to a local **Markdown** file (e.g. `tests/mobile/<platform>/log/last_run_report.md`), then publish with the shared upload script - **a new page per run by default**, so the `--title` prefix carries the run timestamp (the timestamp is part of the unique key here, unlike the case line):

```bash
python ~/.cursor/skills/confluence-publish/scripts/upload_confluence_v2.py --md "tests/mobile/ios/log/last_run_report.md" --space "~712020dbd6441f05734e4da1386119f88cfbe0" --parent 4261085398 --title "<platform> 运行报告 - 全部用例 <YYYY-MM-DD HH:mm>" --version-msg "<platform> run report"
```

   - `--space` takes the space **key** (`~712020dbd6441f05734e4da1386119f88cfbe0`), not the numeric `spaceId`; `--parent 4261085398` is the test_report folder.
   - Because the title carries the timestamp, each run yields its own page and runs never overwrite each other. When "All" is chosen, publish **one page per platform** (each title carrying its own platform name).
   - The script's `--title` prefix dedupe means that if the user explicitly asks to "update the most recent report", you rerun it with **that page's exact existing title prefix** and it updates in place.
3. The returned JSON gives `action` / `page_id` / `version` / `url`; read back by `page_id` to confirm `status=current` and `parentId` equals `4261085398`.
4. Return the **Confluence page link** to the user (one link per page for multi-platform); if there are failed cases, prompt "to fix, connect to `test-debug-script`".

> **Why the script**: a run report with full case tables plus traceback blocks easily exceeds the MCP single-write limit, and the script keeps per-column pixel widths so the stats/case tables stay readable. **Do not** write your own publishing script, **do not** write the page through an Atlassian MCP page-write tool, and **do not** hard-code credentials - the script reads them from `mcp.json`.

> **⭐ Backfilling the Bug column (and any other later edit) also goes through the script — no MCP page write**: after creating Jira Bugs in step (6) you need the `Jira Bug` column of the top summary table filled in. Do it by **editing the local Markdown report (`tests/mobile/<platform>/log/last_run_report.md`) and rerunning the upload script with that page's exact existing `--title` prefix and `--parent 4261085398`** — the script dedupes onto the same page and updates it in place (`action: update`, version bumped). **Never** call an Atlassian MCP page-write tool (`createConfluencePage` / `updateConfluencePage` / `createConfluenceContent` / `updateConfluenceContent`, including the Cursor Atlassian plugin's equivalents). If the local report file is gone, re-read the page with `getConfluencePage` (`contentFormat: markdown`), save it under `tests/mobile/<platform>/log/`, edit, and republish.
>
> ⛔ **Duplicate Atlassian MCP**: if two Jira / Confluence tool sets are visible (`Atlassian-MCP-Server` plus a plugin-provided `*atlassian*` namespace), ask the user to **disable the Cursor Atlassian plugin** (Settings → Plugins / Integrations) and use only `Atlassian-MCP-Server` meanwhile.

> **Body format**: author the report as Markdown and let the script convert it (tables get adaptive pixel column widths). The report body writes **no images/screenshots**; failure evidence is text only. When the script cannot run (credentials missing), save the report to the corresponding platform's `tests/mobile/<platform>/log/last_run_report.md` and prompt the user to publish manually - **do not fabricate publishing success**.
